## 升级步骤

1. 停止旧后端（IDEA 停止按钮，或运行 Maven 的终端按 Ctrl+C）。避免新旧代码同时处理订单。
2. 新后端启动时使用数据库锁和版本校验执行 V001–V003 增量迁移，补齐订单隐藏、捡漏请求、上传资源、评价图片及缓存重试结构。请按 OPERATIONS.md 先备份，并由应用执行迁移。不要重新执行 `girl-shop.sql`、`new-features.sql` 或 `product-data.sql`，它们会清理已有数据。应用账号需要建表及修改表权限；迁移失败会阻止启动并给出错误。
3. 检查旧 RabbitMQ `flash.order.queue` 消息。升级后兼容消费完整 JSON 消息；过期、缺少地址等无法处理的旧请求会进入 `flash.order.failed.queue`，需要人工核对订单及通知买家，不能盲目重放。
4. 在本目录运行 `mvn spring-boot:run`。保留 MySQL、Redis、RabbitMQ 和 Nginx 正常运行，浏览器打开 http://localhost:8090。

## 行为变化

- 普通下单与捡漏预占共用商品行锁。捡漏入口在同一数据库事务内预占库存、持久化订单快照与待投递请求，然后返回请求 ID；此时尚未建成订单。RabbitMQ 消费者异步创建订单，库存不再扣第二次。重复请求复用同一待处理请求，重复消息只创建一张订单。
- 请求表同时作为持久投递记录。投递任务使用持久消息、发布确认和路由返回检查；投递失败或进程重启后按数据库记录重投。消费业务错误最多尝试三次，超过限制或请求超过五分钟后，在事务内标记失败并只恢复一次库存。数据库故障时将当前消息停放到死信队列，数据库恢复后投递记录继续驱动处理。成功订单优先于补偿，过期消息不能重新创建失败订单。
- `GET /order/flash/request/{id}` 仅允许请求所属用户查询；`GET /order/flash/requests` 展示最近请求。前端先显示处理中，再查询结果；等待超过30秒会转到我的订单继续查看，而不是当作下单失败。
- Redis `flash:stock:*`、`flash:order:*` 不再是下单依据。每30秒执行超时请求补偿与库存对账，在商品锁内从数据库重建展示库存并清理旧购买标记、详情缓存。数据库库存已经扣除了待处理预占，不会在 Redis 重启后重新放出这部分库存。Redis 故障不撤销已提交的请求，恢复后再次对账。活动库存调整会拒绝进行中的订单和待处理预占。
- 支付、发货、收货和取消使用订单行锁及旧状态条件；销量及库存随同事务更新。并发失败会返回错误，可重新刷新订单查看结果。
- 待付款订单默认 30 分钟自动关闭，每分钟扫描最多 100 条。包括升级前的旧待付款订单。可通过 `orders.unpaid-timeout-minutes` 与 `orders.expiry-scan-ms` 调整。
- 删除终态订单仅隐藏当前用户列表中的记录，保留交易数据和对方视图。
- 新图片保存于 `/imgs/products/<用户ID>/<UUID>.jpg|png`，校验真实图像格式、文件大小和像素尺寸，并重新编码。资源记录状态为 STAGED / ACTIVE / DELETED。商品或买家秀发布与删除会锁定同一资源记录，避免检查引用与删除之间的竞态；已使用图片不能删除，旧公共演示图片不可删除。历史图片可以由其原商品所有者在编辑时继续使用。
- 验证码使用六位数字，同一手机号发送间隔至少 60 秒，每 120 秒最多尝试五次，验证成功即失效。短信和支付仍是模拟功能。
- 旧捡漏消息的业务错误最多重新入队一次；随后在确认发送到持久失败队列后确认原消息。如果失败队列转存未确认，保留原消息而非丢弃。

## 验证

运行不依赖外部服务的回归测试：

```powershell
mvn test -Dtest=PriorityOneTests
```

测试覆盖重复支付和取消、状态竞争失败的副作用、超时关闭保护、订单隐藏、地址归属、活动结束、自购、捡漏价格、保存失败、假图片、尺寸限制和图片路径越权。服务测试使用模拟 Mapper，不能代替真实 MySQL 行锁、事务回滚或 RabbitMQ 故障测试。

运行真实服务集成测试（需要 MySQL 的建库权限，以及本机 Redis、RabbitMQ）：

```powershell
mvn test "-Dtest=PriorityIntegrationTest" "-Dpriority.integration=true"
```

每次创建 `girl_shop_priority_it_<时间戳>` 临时数据库，测试结束删除；RabbitMQ 使用专用测试队列，Redis 使用专用前缀。不会清空业务数据库或业务队列。测试涉及：

1. 对库存为一的商品同时发起普通与捡漏购买：至多一张成功订单，库存不为负。
2. 同时支付和取消同一订单：最终状态与库存、销量一致；重复取消只回补一次。
3. 在订单扣库存后模拟插入失败：库存事务回滚。
4. 让旧消息重复投递，检查订单 ID 幂等；无法恢复的消息保留在失败队列。
5. 支付与超时扫描并发：已支付订单不被超时关闭。
6. 买家隐藏订单后，卖家仍能查看；上传他人图片地址或删除他人图片被拒绝。

还验证了真实订单 HTTP 接口、请求查询权限、图片接口越权、并发图片删除与使用、RabbitMQ 无路由投递后的恢复以及真实 Redis 对账。测试未通过停止用户的数据库或消息服务制造故障，也未做生产级吞吐压测。

数据库连接明确设置 `+08:00` 会话时区，避免 Java 与数据库调度时间不一致。后台调度开关为 `flash.worker.enabled`，投递间隔为 `flash.dispatch-ms`，对账间隔为 `flash.reconcile-ms`。

本机已运行更新后的 `target/girl-shop-1.0.0.jar`。无需重复启动另一个后端；启动与模拟短信验证码日志在 `.runtime/backend.stdout.log`，错误输出在 `.runtime/backend.stderr.log`。后续修改源码后需重新打包并重启，或者停止该进程再用 `mvn spring-boot:run`。

运行中的服务检查可执行 `mvn test "-Dtest=PriorityLiveSmokeTest" "-Dpriority.live=true"`，它通过 Nginx 检查订单接口和页面，使用检查后即删除的临时用户0会话，不读取现有用户会话。
